# Gradient Reference Option Cleanup Plan

Status: completed. All staged and final behavioral checks passed.

Historical note: this file records an earlier completed interface migration.
The later single-threshold migration removed `grad_reference_relative_tol` in
favor of the sole reference-scaled `grad_tol`; see
`../GRADIENT_STOPPING_SINGLE_THRESHOLD_MIGRATION.md`. The terminology below is
retained as migration history rather than current interface documentation.

## Objective

Remove the historical compatibility options

```matlab
grad_reference_consistency_tol
grad_reference_scale_factor
```

from the eventual public interface of `accelerated_bds_options.m`. The formal
options to retain are:

```matlab
grad_reference_finite_difference_error_tol
grad_reference_relative_tol
```

This cleanup must preserve the solver's numerical behavior. The legacy options
must not be deleted until every in-repository caller has been migrated and the
compatibility conversion has been checked against the corresponding new option.

## Non-negotiable behavioral invariants

Every implementation stage must preserve both invariants below. A stage is not
accepted if either invariant fails, even when the final objective value appears
unchanged.

1. With all acceleration switches disabled, `accelerated_bds_options.m` must be
   exactly equivalent to `src/bds.m` for the same algorithm and explicit solver
   options. Equivalence includes the function evaluation sequence and count,
   returned points and objective values, stopping behavior, exit flag, histories,
   and random behavior.
2. With all acceleration switches enabled, `accelerated_bds_options.m` must be
   exactly equivalent to `tests/competitors/lean_evolved_bds.m` for the default
   algorithm and for explicit `Algorithm='cbds'`, with the same scope of
   equivalence listed above.

The mandatory checker is:

```matlab
addpath(genpath(pwd));
verify_bds_acceleration
```

The checker must pass after every implementation stage. Warnings generated by
the test problems do not count as failures; any `iseqiv` failure or MATLAB error
does count as a failure and blocks the next stage.

## Current compatibility behavior

`set_accelerated_bds_options.m` currently performs two conversions:

1. If `grad_reference_consistency_tol` is supplied, it is interpreted as a raw
   consistency threshold calibrated at `shrink = 0.5` and converted to
   `grad_reference_finite_difference_error_tol` by

   ```matlab
   grad_reference_finite_difference_error_tol = ...
       grad_reference_consistency_tol * 0.5^2 / (1 - 0.5^2);
   ```

   The resulting finite-difference tolerance is subsequently made aware of the
   public `shrink` value. The current default conversion gives raw threshold
   `0.1` when `shrink = 0.5`.

2. If `grad_reference_scale_factor` is supplied, it is interpreted as

   ```matlab
   grad_reference_relative_tol / grad_tol
   ```

   and converted by

   ```matlab
   grad_reference_relative_tol = ...
       grad_reference_scale_factor * grad_tol;
   ```

The migration must preserve these conversions exactly for all supported option
values, including non-default `shrink` and `grad_tol` values.

## Staged execution

### Stage 0: Baseline and inventory

- Record the clean baseline result of `verify_bds_acceleration`.
- Enumerate every code, test, experiment, profile, and documentation occurrence
  of both legacy option names.
- Classify each occurrence as an input option, compatibility conversion, test
  fixture, experiment label, or prose reference.
- Do not edit solver behavior in this stage.

Acceptance gate: the baseline strict checker passes, and the inventory is
complete enough that no legacy occurrence is migrated implicitly or overlooked.

### Stage 1: Migrate in-repository callers while retaining compatibility

- Replace legacy option assignments in tests and experiments with equivalent
  assignments to the formal options.
- Update documentation and experiment descriptions to use the formal options.
- Keep the compatibility conversion in `set_accelerated_bds_options.m` so that
  external or not-yet-migrated callers still work during this stage.
- Add focused checks comparing each old-form input with its explicitly converted
  new-form input, including non-default `shrink` and `grad_tol`.

Acceptance gates:

- `verify_bds_acceleration` passes.
- Existing gradient-stop regression checks pass, including
  `verify_gradient_stop_no_extra_evaluations`.
- Focused old-form versus converted-new-form checks show identical outputs,
  histories, stopping decisions, and evaluation counts.

### Stage 2: Remove the compatibility interface

- Remove acceptance, validation, conflict checks, and conversion code for
  `grad_reference_consistency_tol` and `grad_reference_scale_factor`.
- Retain the internal raw threshold needed after applying `shrink`, but give it
  an internal name that is not a public option name, such as
  `grad_reference_raw_tol`.
- Update error messages and option documentation so only the formal options are
  advertised.
- Confirm that no repository caller or documentation reference remains, except
  in this plan's migration history if needed.

Acceptance gates:

- `verify_bds_acceleration` passes again.
- All gradient-stop regression checks pass again.
- The focused formal-option tests cover default and non-default `shrink` and
  `grad_tol` values.
- Repository search reports zero remaining legacy option occurrences outside
  explicitly historical records.

### Stage 3: Reformat and document termination options

Only after Stage 2 passes:

- Decide final names for the remaining formal termination options.
- Align every option description with the longest variable name plus three
  spaces, matching the acceleration-options style.
- Put the first description text on the same line as each variable name.
- Use explicit sentences and avoid unexplained legacy terminology or ambiguous
  pronouns.
- Keep `Default:` on its own aligned line.

This stage is documentation-only unless a separately reviewed public option
rename is explicitly approved. Run the strict checker after the formatting
changes as an additional safeguard.

## Prohibited shortcuts

- Do not delete the legacy conversion before all in-repository callers have been
  migrated.
- Do not replace a legacy tolerance with a guessed constant. Use the exact
  conversion equations above.
- Do not accept matching final `xopt` values as sufficient evidence of
  equivalence.
- Do not modify acceleration algorithm code as part of this option cleanup.
- Do not proceed to the next stage after a failed strict checker.

## Completion criteria

The cleanup is complete only when the two legacy options have been removed from
the public interface, all in-repository callers use the formal options, the
termination documentation is aligned and explicit, and every mandatory and
focused behavioral check passes.
